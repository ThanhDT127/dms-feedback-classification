### Triệu chứng Lỗi & Trải Nghiệm Người Dùng
Web service gặp hiện tượng tải rất chậm (lag, freeze) trên hầu hết các tab (`#analytics`, `#files`, `#classify`, `#logs`, `#settings`). Khi một người dùng mở tab Files hoặc preview một file Excel lớn, toàn bộ các request từ các tab khác đều bị đứng hình.

### Nguyên nhân Gốc rễ
1. **Event Loop Starvation**: Service chạy Gunicorn với 2 worker Uvicorn. Nhiều endpoint khai báo `async def` nhưng trực tiếp gọi các hàm I/O blocking đồng bộ (Microsoft Graph API qua `requests`, parse workbook Excel bằng `openpyxl`/`pandas`, đọc file log 10MB bằng `read_text().splitlines()`) trên main thread của event loop.
2. **Quét toàn bảng & Deserialization thừa thãi**: Endpoint `GET /api/metrics` đọc toàn bộ kết quả phân loại từ bảng `classification_job_results` và chạy vòng lặp `json.loads` trong Python để tính nhãn.
3. **Danh sách Job quá nặng**: Endpoint `GET /api/classify/jobs` trả về toàn bộ payload kết quả chi tiết cho tất cả các job thay vì chỉ trả metadata.

### Quy trình Sửa Lỗi Đã Xác Minh
1. **Async Decoupling với ThreadPool**: Sử dụng `starlette.concurrency.run_in_threadpool` để bọc toàn bộ các lệnh blocking (SharePoint API, đọc/ghi Excel, tail file log).
2. **In-Memory TTL Caching**: Áp dụng `SharePointListCache` (TTL 45s) và bộ đệm sản phẩm với kiểm tra `st_mtime` cho danh mục Excel.
3. **SQL Indexed Aggregation**: Thay thế quét JSON payload bằng câu lệnh SQL `SELECT label, COUNT(*) FROM feedback_labels GROUP BY label` (<1ms).
4. **Binary Reverse Log Tail Seeking**: Dùng `seek(pos)` từ cuối file nhị phân theo khối buffer 64KB, tăng tốc độ đọc log lên 46.8 lần mà không tốn bộ nhớ.
5. **Lightweight Job Listing**: Mặc định `include_results=False` và phân trang `limit=50, offset=0` cho endpoint danh sách jobs.
